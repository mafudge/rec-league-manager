# v0.2.0 Frontend Ports (Streamlit, Flutter) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** the Streamlit and Flutter (web) frontends run every v0.2.0 story against any of the four backends, so all 12 pairings run the PRD demo; then the release closes.

**Architecture:** Each frontend gets one API client that mirrors the web client (`src/frontends/web/app/api.ts`): it attaches the bearer token, refreshes once on a 401 with the newest `refresh_token`, turns a 4xx with an `error` body into `BackendRefused(message)`, a server error into "The backend had a problem (n)", and a network failure into "Can't reach the backend at <API_URL>". Screens follow PRD §6 and the web app: sign up, sign in, league list, create league, league home with Entrants · Schedule · Standings and the public link, and the public page. Frontends never write validation messages of their own.

**Tech Stack:** Streamlit 1.64 + `requests` + Streamlit `AppTest`/pytest (`src/frontends/streamlit`); Flutter 3.44 web + `http` + `flutter_test` with `http/testing.dart`'s `MockClient` (`src/frontends/flutter`).

**Spec:** `docs/superpowers/specs/2026-10-24-v0.2.0-release-design.md` (§7). **The contract:** `src/README.md`. **The reference UI:** `src/frontends/web` (screens, copy, behaviour) and `docs/design/`.

## Global Constraints

- Messages shown to the user come from the backend's `error` field, verbatim, plus exactly three client-side texts the web app uses: "Can't reach the backend at <API_URL>", "The backend had a problem (<status>)", and the empty states/labels the web app shows ("No leagues yet — create one.", "No entrants yet — add the first one.", "No schedule yet — add entrants, then generate.", "No games played yet", "No games scheduled yet", "League not found", "Regenerate the schedule to include new entrants.", "Clear every score in this league?", tiebreak sentence comes from the backend).
- **Bodies (Firebase rule):** send no body and no `Content-Type` on routes that take none (GET, `POST …/schedule`, `DELETE …/scores`); send a JSON object with `Content-Type: application/json` otherwise.
- Refresh: on a 401 from a 🔒 call, refresh once with the newest `refresh_token`, save the new pair, retry once; refresh answered 400/401/403 → forget tokens and go to sign in; any other refresh failure keeps the session and shows the backend-problem text.
- Blank score boxes are sent as `""` (so the backend's whole-number message shows); only "Clear" sends both `null` (US05-01).
- Ties: hide the T column and accept ties only as the backend decides; the T column shows only when `allow_ties`.
- 375 px wide, no horizontal page scroll; on the public page, this week's games come first.
- Token storage: Streamlit `st.session_state`; Flutter in memory (spec §7; lost on reload, accepted).
- Public link: Streamlit `?league=<slug>` (no path routing); Flutter `/#/l/<slug>` (hash URL strategy, so a deep link works without server rewrites); "Copy public link" copies this frontend's own URL and also shows it as text.
- Every pairing works: run each story against FastAPI while building; the release check runs all four backends.
- Branches `dev/<issue>-<slug>` off `release/v0.2.0`, merged by the controller. Product questions → stop and ask (spec §4).

## Review Focus

1. **A message the frontend wrote itself** instead of the backend's `error`. (All tasks)
2. **A body sent on a bodiless route** (breaks Firebase only). A client test asserts no body/`Content-Type` on `POST …/schedule` and `DELETE …/scores`. (Tasks S1, F1)
3. **Refresh using an old refresh token, or refreshing in a loop.** (Tasks S1, F1)
4. **Streamlit reruns** re-sending a form action (double add, double generate) on the next interaction. (Tasks S2–S3)
5. **Flutter `MockClient` tests that never exercise the real URL/headers** — assert method, URL, headers and body on each call. (Tasks F1–F4)
