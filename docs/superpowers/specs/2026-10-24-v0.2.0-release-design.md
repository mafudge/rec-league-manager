# v0.2.0 release design: the MVP on every backend and frontend

*Written 2026-10-24 from a planning conversation with the organizer (product owner, Michael Fudge). Decisions marked **(theirs)** were made by them; **(my call)** were made in planning and can be overruled.*

## 1 · Intent

Rec League Manager is the worked example for IST300. Students compare 4 backends (FastAPI, Django, Supabase, Firebase) and 3 frontends (Next.js web, Streamlit, Flutter web), all speaking one REST contract (ADR 003). Today every pairing only says hello. v0.2.0 makes every pairing a working league manager: an organizer can sign up, sign in, create a league, add entrants, generate a round-robin schedule, record scores, see standings, and share a public link players open without signing in.

Because it's a reference example, **all 12 pairings must work (theirs)**. The point students should take away is that the same product, behind the same contract, can be built very differently.

## 2 · Scope

**In v0.2.0 (theirs):** the eight Must stories in `docs/backlog.md`, in this order:

US13 sign up → US01 sign in → US02 create league → US03 add entrants → US04 round-robin schedule → US05 record score → US06 standings (with US06-01 folded in) → US07 public link.

The acceptance criteria in the backlog are the requirements, verbatim (PRD §4). Decisions from planning that are already written into the backlog and PRD:

- **Sign-up exists (theirs).** US13: email + password of at least 8 characters, signed in immediately, no email confirmation. Each organizer sees and changes only their own leagues.
- **Weeks follow the schedule (theirs).** US04: generate the full round-robin, set the league's weeks to match (up or down, the down direction is my call), and tell the organizer.
- **Ties are a per-league setting (theirs).** US02 adds "Games can end in a tie", off by default (my call). In a league that allows them, US05 saves a tied score and US06 shows a T column; in one that doesn't, US05 refuses it with "This league doesn't allow ties" and there's no T column (hiding it is my call). Sort stays W → Diff → PF, then name (my call: ties don't affect sorting).
- **US06-01 (#15) is folded into US06 (my call).** It's already labeled v0.2.0.
- **Clear all scores (theirs).** US04's refusal says "clear them first", so the schedule screen gets a "Clear all scores" button with a confirmation step. Every game becomes unplayed and the schedule is kept. AC added to US04.
- **No deadline (theirs).** The course dates in PRD §9 don't apply to this reference build. The release is done when all 12 pairings work, however long that takes.

**Not in v0.2.0:**
- US08–US12 (Should/Could).
- US14 forgot password (theirs: backlog). It needs email, which PRD §3 rules out this semester.
- REL-01 deploying every release (theirs: backlog, to be designed later).
- Sign in with Google (my call: backlog). US01 says email + password, and Google would need every student to set up a Google Cloud OAuth client, undoing ADR 001's "no Google account".

**Anti-goals.** Any of these makes the release a failure, even if the screens work:
- A frontend that knows or branches on which backend it's talking to.
- Two backends that answer the same mistake with a different status or message.
- Standings stored anywhere (PRD §5: computed on every request).
- A public page with any control that writes, or that asks a player to sign in.
- A story marked done without tests.

## 3 · How the work is ordered

**Build one pairing, then port (theirs, on my recommendation).**

1. **Reference build: FastAPI + Next.js web.** Every story, end to end, in the order above. Each story adds its routes to the contract (`src/README.md` route table, `docs/03-architecture.md` §4) and to `src/contract-test.sh`. FastAPI was chosen because it already computes standings (#14); web because it's the phone-first UI in the PRD (my call).
2. **Backend ports, in this order: Django, Supabase, Firebase.** A port is done when `src/contract-test.sh` passes against it and the web frontend runs the demo path against it.
3. **Frontend ports: Streamlit, then Flutter.** Built against FastAPI; the contract test already guarantees the other backends answer the same way.

**Issue granularity (my call).** One issue per story in the reference build (8 issues). Each port is split into four issues by story group, so each stays small enough for a moderate programmer:

| Group | Stories |
|---|---|
| Accounts | US13, US01 |
| Leagues and entrants | US02, US03 |
| Schedule and scores | US04, US05 |
| Standings and public page | US06, US07 |

That's 3 backends × 4 + 2 frontends × 4 = 20 port issues, 28 issues in all. A port issue for a group starts only after the reference issues for that group are merged.

## 4 · Branches, labels, and process

- **Before the branch is cut (my call):** the planning changes to `docs/backlog.md`, `docs/02-prd.md` and this document are committed to `main`, so the release starts from a clean tree (CLAUDE.md rule 13). #15 (US06-01) comes off the todo list and is closed by the US06 reference issue, which carries both the `US06` and `US06-01` labels. #14 (standings calculation, already merged) is the starting point for that issue, not a separate one.
- **Release branch (theirs):** `release/v0.2.0`, cut from `main`.
- **Feature branches (theirs):** `dev/<issue>-<slug>`, cut from `release/v0.2.0` and merged back into it with `--no-ff`. Nothing goes to `main` until the release is done.
- **Release done:** all 28 issues are closed, the checks in §8 pass, and `release/v0.2.0` merges to `main` with a `v0.2.0` tag.
- **CLAUDE.md** rules 9 and 13 say feature branches go to `main`. I'll update them to describe release branches (my call; it's the process the organizer asked for).
- **Labels:** every issue gets `v0.2.0` plus its story labels (`US13`, `US01`, …), plus `backend` and/or `frontend`. Missing story labels get created.
- **Todo and changelog:** issues move through `docs/todo.md` → `docs/xchangelog.md` as in v0.1.0.
- **Decisions during the run (theirs).** When building surfaces a bug, a gap or a choice the backlog doesn't settle, stop and ask the organizer whether to fix it in v0.2.0 or put it on the backlog for a later release. Don't guess and keep going.

## 5 · The contract additions

The route list is fixed here. Field names and response shapes are fixed by the reference build, story by story, and written into `src/README.md` and the contract test as each one lands. After that, the ports follow them exactly.

**Auth (US13, US01).** One shape for every backend; each backend implements it with its own sign-in system (my call, also planned in `docs/03-architecture.md` §5):

| Backend | Behind the contract |
|---|---|
| FastAPI | bcrypt-hashed passwords in SQLite, signed JWT |
| Django | Django's built-in `User` and DRF token auth |
| Supabase | Supabase Auth (GoTrue) email/password, with email autoconfirm on; the Edge Function proxies it |
| Firebase | Auth emulator email/password; the Function verifies the ID token |

- `POST /api/auth/signup` `{email, password}` → `201 {token, refresh_token}`, or 400 with the US13 messages.
- `POST /api/auth/login` `{email, password}` → `200 {token, refresh_token}`, or `401 {"error": "Email or password is incorrect"}` (the same message whether or not the email exists).
- Every route that changes data, and every organizer read, needs `Authorization: Bearer <token>`. Missing or bad token → `401 {"error": "Sign in required"}`, and the frontends send the organizer to sign in.
- **Sessions behave the same on every backend (my call).** Firebase and Supabase tokens expire after an hour, DRF tokens never do, and FastAPI's last as long as we choose. So the contract promises the shape, not the lifetime: `POST /api/auth/refresh` `{refresh_token}` → `200 {token, refresh_token}`, or `401 {"error": "Sign in required"}`. Every frontend, on a 401, tries one refresh and retries the request; only if that fails does it send the organizer to sign in. Each backend maps refresh onto its own system (Firebase's secure-token refresh, GoTrue's refresh grant; FastAPI and Django issue their own refresh token and give access tokens a 1-hour life, so all four behave alike). An organizer stays signed in through league night on any backend.
- **Sign-out is client-side (my call):** the frontend forgets both tokens. No server route; revoking tokens goes on the backlog if it's ever needed.
- Another organizer's league answers `404 {"error": "League not found"}`, not 403, so leagues can't be probed (my call).
- A short ADR 004 records "one sign-in contract, four implementations" (my call).

**Product routes** (all under `/api`):

| Route | Story |
|---|---|
| `GET /leagues`: my leagues | US02 |
| `POST /leagues` | US02 |
| `GET /leagues/{id}` | US02 |
| `GET /leagues/{id}/entrants`, `POST /leagues/{id}/entrants` | US03 |
| `POST /leagues/{id}/schedule`: generate or replace; returns the weeks and, when weeks changed, the US04 message | US04 |
| `GET /leagues/{id}/games`: by week, byes included | US04 |
| `DELETE /leagues/{id}/scores`: clear every score, keep the schedule | US04 |
| `PUT /games/{id}/score` `{home_score, away_score}` | US05 |
| `GET /leagues/{id}/standings` | US06 |
| `GET /public/{slug}`: league (name, location, sport, season), games by week, standings, and which week is current; no auth | US07 |

Validation messages are the ones in the acceptance criteria, word for word, returned as `{"error": "..."}` with status 400 (409 for a duplicate entrant name or email is the builder's call, but it must be the same on every backend).

## 6 · Data

PRD §7 is the model: Organizer, League, Entrant, Game; standings are never stored.

- **League** gets a `slug`: a short random code (like `k7q2xm`) for the public link, not a sequential id (my call, the PRD's lean). Public pages live at `/l/{slug}` in every frontend.
- **A bye is a Game with no away entrant (my call).** `compute_standings` in FastAPI already treats it that way.
- **"Current week"** for the public page: the lowest week that still has an unplayed game; once every game is played, the last week (my call).
- **Storage** follows `docs/03-architecture.md` §5: SQLite via SQLAlchemy (FastAPI), SQLite via the ORM (Django), Postgres (Supabase), Firestore (Firebase). Data survives restarts (PRD §5).
- **Firebase keeps its data too (my call; PRD §5 requires it).** `npm run emulators` starts with `--import` and `--export-on-exit` on a git-ignored directory, which closes the gap in `docs/03-architecture.md` §8. The Firebase Accounts port issue does this and tests a restart.

## 7 · Frontends

- **Screens** follow PRD §6: sign up, sign in, league list (with the empty state), create league, league home with Entrants · Schedule · Standings and a copyable public link, and the public page. The prototypes in `docs/design/` (`prototype.html`, `web-prototype.html`, `walkthrough.html`) are the visual reference.
- **375 px, no horizontal scrolling** on every screen (PRD §5). On the public page, this week's games show above the fold.
- **Errors come from the backend.** Frontends display the backend's `error` message, the same as for hello today.
- **Where the token is kept (my call):** web keeps it in `localStorage`, Streamlit in `st.session_state`, Flutter in memory (it's lost on reload, which is acceptable for a stub-grade port; it goes on the backlog if it annoys).
- **Streamlit** is noted in the architecture doc as awkward for a public phone page. It still gets every screen; its public page is a query-param route (`?league=<slug>`), since Streamlit has no path routing (my call).

## 8 · Definition of done

**Each issue:**
- Unit tests for the logic, plus integration tests through the HTTP routes (backends) or the rendered screens (frontends), one per acceptance criterion where practical.
- All of the folder's tests pass; the server starts; the app runs the story's path live without error.
- Backend issues: `src/contract-test.sh` passes against that backend.

**The release:**
- `src/contract-test.sh` passes against all four backends, run at the same time.
- The PRD demo path (sign up, create "Tuesday Cornhole", add 6 teams, generate, enter week 1 scores, open the public link at 375 px) runs on each of the 3 frontends against each of the 4 backends: 12 runs, recorded in the release's changelog entry.
- `docs/03-architecture.md` §4 and §5 and every README match what was built.
- Everything that was started has been stopped (CLAUDE.md).

## 9 · Left to the builder

Field names and JSON shapes (fixed once, in the reference build); table and collection layouts; libraries within each stack (for example PyJWT and bcrypt); the round-robin algorithm (circle method is the obvious choice, as long as the US04 bye rule holds); styling, as long as it stays close to `docs/design/`; test file layout.
